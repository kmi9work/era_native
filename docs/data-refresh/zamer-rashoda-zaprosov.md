# Расход запросов на один открытый экран (5 минут)

Пункт DoD «расход запросов на один открытый экран цеха за 5 минут измерен и записан»
из `TZ-edinyy-sloy-dannyh.md` (§ 9).

## Что измерено и как

Полевой замер на планшете мастера **не выполнен** (нет доступа к устройству из этой
среды). Ниже — расчёт по фактическим TTL и интервалам опроса из `src/data/hooks/*`
(`npx jest __tests__/data` подтверждает, что задержки и backoff работают как задумано).
Числа в таблице — верхняя оценка для экрана, который открыли один раз и держали
в фокусе 5 минут без возвратов на него:

    запросов = (1 на ключ при первом входе) + 300 с / интервал опроса

Опрос идёт только пока экран в фокусе (Д4) и только один таймер на ключ, поэтому
повторные входы на экран добавляют только refetch-on-focus (по 1 запросу на ключ).

| Экран | Ключи и их режим | Запросов за 5 мин |
|---|---|---|
| Цех → «Выбор гильдии» | `guilds` (TTL 60 с, без опроса) | **1** |
| Цех → «Предприятия гильдии» | `guild:id:plants` (TTL 15 с, опрос 30 с) + `guilds` | **11–12** |
| Цех → «Выбор типа предприятия» | `plantLevels` (TTL 300 с, опрос 60 с) + `availablePlaces` (TTL 60 с) | **7** |
| Цех → «Улучшение предприятия» | `plant:id` (TTL 0) + `plantLevels` (опрос 60 с) + `resources` (опрос 60 с) + `guilds` | **14** |
| Цех → «Много предприятий» | `resources` + `plantLevels` (оба опрос 60 с) | **12** (+`plant:id` на каждый скан) |
| Рынок (форма расчёта открыта) | `countries` (опрос 30 с) + `prices` (опрос 60 с) + `guilds` + `robbery:id` (TTL 30 с, без опроса, на каждую гильдию) | **≈26** при 4 гильдиях |

Максимум — на рынке: ~26 запросов за 5 минут (≈5 в минуту). Самый тяжёлый по размеру
ответа ключ `plantLevels` (весь справочник) опрашивается раз в 60 с, то есть 5 раз за
5 минут и только на экранах, где он реально нужен.

## Что изменилось относительно прежнего поведения

- Раньше каждый вход на экран делал полную загрузку (несколько запросов подряд) без
  учёта свежести и дедупликации: возврат на список предприятий = повторный запрос
  даже если данные получены секунду назад. Теперь возврат внутри TTL не делает запроса.
- Рынок раньше держал **два** `setInterval` (страны 30 с и «обновление рынка») и
  дублировал загрузку двумя путями; сейчас один таймер на ключ, а тяжёлый
  `show_prices` опрашивается раз в 60 с, а не при каждом цикле.
- При ошибках интервал растёт экспоненциально до 5 минут (backoff) с jitter 10 %,
  поэтому при недоступном бэкенде опрос не спамит.

Точных «до/после» в цифрах нет: счётчиков запросов в приложении до этого этапа
не было, а логи бэкенда за прошлые периоды недоступны.

## Как воспроизвести полевой замер

1. Развернуть сборку на планшете мастера, открыть целевой экран, не трогая его 5 минут.
2. Смотреть access-лог бэкенда по IP планшета за этот интервал:
   `grep <ip> /var/log/nginx/access.log | awk '{print $7}' | sort | uniq -c`.
3. Либо снять счётчик из клиента: `queryClient.stats()` даёт число ключей и запросов
   в полёте; для счётчика за интервал достаточно логировать каждый вызов `startFetch`
   в `src/data/queryClient.ts` (одна строка `console.log(entry.keyString)`).
4. Повторить для «до» на предыдущей сборке тем же способом — только так получится
   честное сравнение.
